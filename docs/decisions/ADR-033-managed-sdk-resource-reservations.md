# ADR 033 — resource reservations follow actual managed SDK lifetime

Status: cooperative native resource reservations integrated with managed Store activation; installed-version reclamation/audit/Host/JNI adoption remain open. Component evidence is recorded separately.

Every resource-backed managed activation acquires a shared advisory reservation before loading its bounded verified snapshot. Recogniser/converter wrappers retain that reservation with the actual provider owner. Existing Adapter Arcs consequently retain it through candidates, Ready publication, detached owners and in-flight jobs. The legacy Store recogniser/converter activation paths also wrap their providers. Resource-free adapters retain their existing behavior. Raw Manager APIs that receive only bytes do not assert ownership of an unspecified disk path; trusted callers must separately retain a guarded reader for resources they own.

Factory captures are owned by a guard-aware holder before snapshot loading. A preconstructed provider captured by a factory therefore retires under the reservation even if loading fails before the callback runs. Provider-owned I/O error payloads are disposed under the reservation before returning a safe error classification. Actual provider destructors run before the reservation closes. Provider callback/construction/destructor panic marks retirement uncertain, attempts a content-free persisted review marker and intentionally retains one shared reservation for that failed pin until process exit. The latch prevents repeated retention by the same pin. A nonempty marker refuses subsequent acquisition/removal with ReviewRequired; there is no automatic marker reset or claim of SDK quiescence after failure.

Stable `.stem-resource-<SHA256(filename bytes)>.lock` control files live alongside the resource. The key is independent of the registry instance, version ID and parent-directory spelling, so different versions/registries using the same actual pathname cooperate, including through a separate process. A parent rename retains its control filename/inode. Coordination files are never unlinked by this module and their reserved names cannot themselves be treated as resource payloads. Nonregular/symlink or nonempty control files fail closed. Shared acquisition rejects symlink/nonregular payloads; exclusive coordination can still be acquired after a known payload is absent for later explicit recovery. This is cooperative private-depot coordination, not protection against arbitrary privileged code replacing filesystem names.

`ResourceLeases` now obtains the same OS reservation in addition to its existing reader-count bookkeeping. Independent registry removal requires an exclusive nonblocking reservation. Existing public active-reader removal keeps its Conflict result. Reader clones keep guarded handles and close the last actual descriptor before releasing the reservation. The stable control file remains after physical removal. No SDK callback, hashing or file operation is added to the Host writer's metadata publication path.

This increment does not yet authorise installed-version disk deletion. Production reclamation still needs a fresh explicitly authorised Removed-version plan, durable action metadata, exclusivity over transfer/resource namespaces, safe partial-outcome recovery and Host/JNI/Android lifecycle integration. Manager absence or logical Removed remains insufficient evidence that all resource owners retired. Hard termination/isolation, global cross-media scheduling, actual recogniser rights/quality and device acceptance remain open. Synthetic fixtures establish component lifetime behavior only.
