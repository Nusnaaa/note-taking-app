## §0.8.4 Model-and-converter architecture — owner-approved direction, proposed implementation details

**Approved direction:** one shared installation/readiness/version/selection manager; **separate specialised adapters** for (a) digital ink to transcribed maths/prose/numerals/code, (b) content-to-content converters, and (c) **future optional** local or explicitly authorised remote generative models. It is incorrect to claim every engine is compatible with one generic byte-stream inference call or that changing a file always constitutes switching a compatible model.

**Authoritative core:** the app owns original pen trajectories, document identity/history/permissions, structured editable maths, prose and code; models have no direct authoritative write privileges. Recognition uses a frozen, provenance-labelled immutable source snapshot and returns a **proposal**. Before accepting the proposal the core compares source identity/revision; stale or cancelled responses are rejected or explicitly reconciled, never applied over new ink silently. Engine changes/removal cannot delete user-authored or accepted content, original ink, or corrections.

**Engineering contract candidates requiring precise review/implementation validation:**

- Source-ink schema: ordered strokes and points, stroke/time/coordinate basis, available pressure/tilt/buttons, distinction between absent and zero values, transform and version identifiers. Pen predictions, smoothing and model normalisations are derived and reversible, not substitutes for observed authoritative ink.
- Recognition request/result: requested task (`math`, `text`, `numeric`, `code`, or explicit mixed partition), immutable region/source fingerprint, recogniser/adapter version and capabilities, candidates/alternatives, parse diagnostics, nullable/uncalibrated confidence and any qualified source associations. No unsupported per-symbol mapping should be fabricated.
- Editable math: a presentation/notation-oriented structure able to retain incomplete expressions and ambiguity (e.g. incomplete brackets, holes, unparsed macros and unknown tokens), with optional **separately approved** semantics rather than forced symbolic simplification. Exact node vocabulary, supported structural editing and H.I. correction behaviour remain design candidates, not an adopted library.
- Converter: declare input/output dialects and limits, never silently solve/normalise maths or alter code whitespace; retain original source and meaningful diagnostics plus evidence of lexical/layout/lossy changes. Round-trip fidelity must be **tested and scoped**, not universally presumed.
- Engine manifest: common identifier, provider/family, task/capability profile, source input/output contracts, runtime ABI, expected model/decoder/tokeniser dependencies, licence/network disclosures, resource profile and provenance. Add type-specific fields, including whether required raster input/preprocessing exists or internals are undisclosed. Examples supplied by Work research are illustrative, not accepted shipping schemas.
- Lifecycle: staged verified install or owner-controlled import, explicit consent to necessary external model-download/activation traffic, readiness states, cancellation, resource limits, crashes/timeouts, version handling and accurate disclosure when an SDK does not expose app-owned weight pinning or rollback. Unknown support must remain unknown.
- Model manager H.I. on completed build: transparent install/readiness, compatible candidate discovery, default/per-operation choices, easy switching/removal and local comparison of result quality. Do not enable a model that cannot satisfy a task's declared input contract; an adapter can be written where practical without requiring a rebuild of authoritative stored content.

**Not approved:** any named recognition SDK, model weight, vendor, runtime/version, internal-raster claim, undocumented network permission, commercial arrangement or automatic output-acceptance gesture. The owner approved the architecture **direction**; lower-level library or schema proposals remain technical decisions subject to implementation validation and relevant owner approval.

## §0.8.5 Recognition approval interaction — preserve previously approved explicit acceptance

**Existing binding owner precedent Q084 and REC-006 / NB-REC-001:** recognition and acceptance are **distinct actions by default**. A user-initiated manual Convert action produces a reviewable, non-blocking editable transcription proposal; it does **not** automatically replace or reflow original ink. The user can accept, correct, partially accept or reject; accepted output takes the selected region in place while original source ink remains durably recoverable. Assisted/background recognition may prepare unobtrusive proposals but must never silently commit them, and stale/late results cannot overwrite later changes. The owner previously treated a future **opt-in** auto-accept experience as a possible later alternative, not a first-release obligation.

The 21 October external research review raised a usability question about additional confirmation taps; it does **not** itself supersede explicit Q084. The approved preview-and-accept default therefore remains the normative baseline. A one-step user-triggered insertion with Undo is **not approved** and should only be re-opened if the owner later explicitly requests it; no extra question is needed to proceed under the existing contract. Implement H.I. review to be low-friction within these boundaries.

## §0.8.6 Local security, backup, export and portable import — binding behavior

- I0/I1 security follows the **Samsung Notes-like experience with normally unlocked notes and optional locks** backed by Android device encryption/sandbox and application-level access checks (**Q19 Option A**). Do not assert separate working-database/per-object-at-rest encryption or advanced full-store encryption in I1; stronger encryption only if later specifically requested, not commercially motivated by default.
- Locked material shall be suppressed in unauthorised H.I. projections, search, previews, clipboard, model requests and diagnostics. A lock is not proof that the copied raw database contains ciphertext. Distinguish app access control from threat conditions where an attacker extracts app files.
- Disable implicit OS cloud backup of notebook contents (and verify OS/device-transfer settings). Use explicitly initiated encrypted comprehensive backups. User-controlled ordinary native document exports may be plaintext when no protected material or once appropriate permissions have been granted.
- If any protected content is selected for export, **before producing the output** present protected/unprotected choices, and **reauthenticate for both** choices. Protected path encrypts the **whole package** and should not leak sensitive metadata; plaintext path explicitly warns that selected locked material will be exposed in the export. Original local locks remain unchanged whichever choice is made.
- Encrypted portable export uses a **transferable credential** set/authorised by the exporting user, not device-only biometric/Keystore. Recipient enters this credential on import to authorise opening, then may establish local destination credentials. An unauthenticated short PIN alone must not be misrepresented as robust resistance to offline brute force; derive and enforce an appropriate cryptographic credential policy under backend security testing. The owner's preference for an approachable PIN/password ceremony should be respected in H.I. design.

### Stage 5A — Q383 accepted source-retention and revocation contract

For an accessible source in a first-release PDF link or later Module Resources system:

1. Independent user-authored writing (including source-ink, recognised text, Notes and analysis) remains accessible subject to the owner's own locks and access rules when a live source permission ends.
2. Retained historical excerpts/snapshots MAY remain readable only when **independently authorised continuing retention** exists. The retained asset MUST record source identity/revision/capture time/authority and display as an old snapshot, never as a still-accessible live source. A future restriction that validly cancels continued retention MUST be enforced.
3. Revoked source bytes MUST NOT remain readable through live viewers, caches, thumbnails, search indexes, exports, AI channels, child/parent Module browsing or cached renderers. Ordinary cached data are not equivalent to independently authorised snapshots.
4. Pending edits to a source whose write permission is lost MUST remain available for safe non-publishing review without silently uploading, changing or deleting the source. User-authored work is not sacrificed to source revocation.
5. None of the above extends licence, contractual sharing, external export or cloud-inference rights. Backend evaluation MUST enforce actual permitted scope and revalidate before export.
